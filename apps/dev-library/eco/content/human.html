1. The surface defined

1.1 What the Human Design Surface is

The Human Design Surface is the complete, executable design system for every human-facing surface in the UZE ecosystem: web pages, the UZE Dev Library, emails, generated documents that carry the brand, and the rendered output of any repo in the estate — including surfaces that do not exist yet and surfaces deployed under a client's own brand.

It is a system, not a style guide. A style guide is a document a person may or may not open. This system is built so that the standard is executable: the values are data (one canonical file), the rules are written once (one house skill), every repository carries an anchor that points at both, and a verification gate — the car wash — sits in the deploy path of every anchored repo, so a page that violates the system does not deploy. The sensitivity is resident in the machinery, not dependent on anyone remembering it.

The system was created on James's direction of 2026-11-19 (~00:06 ET): the design sensitivity must be a global sensitivity — anchored in every new repo and all existing repos, resident in any white-label or multi-tenant engagement, and run as a pre-deployment car wash before any page deploys — so that simplistic design errors stop costing the founder hours of catching them by eye. The immediate cause was concrete: on 2026-11-18, two errors reached James's phone that a written system plus a verification step would have caught first — a wordmark that wrapped to two lines at phone width, and red and green status colors sitting in a page whose approved system contains no red or green anywhere.

1.2 Who it serves

  • Humans on every UZE surface. Readers, development partners, talent, clients, and the public, on uzemarkets.com, dev.uzemarkets.com, the AEInfo surfaces, Fundio, the shared Command & Control Console, and every surface that follows. UZEmarkets launches January 2, 2027 and is a prospective project; Learn2Launch is the present phase. This system governs the design of both, and does not change what either is.
  • Enterprise and larger-SME white-label clients ($15–35M+ class). Engagements of that size require extreme UI/UX sensitivity as a condition of the work. Under this system a tenant deployment inherits the full standard — structure, verification, and all — and customizes only token values (Section 3.4). The design sensitivity stays resident inside the client's deployment because it is enforced by the gate in their deploy path, not by a document handed over at kickoff.
  • The people who build and steer. James, who ratifies; Jonathan Schmidt and his Fort Lauderdale motion-graphics collaborator, who advise; and every human or agent who opens a repo and meets the anchor before touching a branded surface.

1.3 The pairing with the Agentic Design Surface

James named two counterpart design systems on 2026-11-19:

  • HUMAN ECOSYSTEM DESIGN — this system. Human-facing surfaces: what a person sees, reads, and judges.
  • AGENTIC ECOSYSTEM DESIGN — the counterpart. Agent-facing surfaces and the infrastructure agents act through, covered by the companion document, Agentic Design Surface for UZE Ecosystem.

2. How it works — the five-part mechanism

The mechanism is one chain of five parts. Each part exists because the part before it is not sufficient alone.

2.1 One canonical source of values

Every design value in the ecosystem resolves from a single file: ~/workspace/design-anchor/tokens.json — the eight-token palette, the type scale, component geometry, the wordmark rules, and the standing rule that no other hues exist anywhere, status feedback included (Section 3 states the values in full).

Beside it, tokens.css carries the same values as CSS custom properties. It is generated from the JSON, and the two were verified mechanically at creation: identical color and size value sets. The house skill carries the same system as rules in words — why each rule exists, and the mandatory pre-ship check.

Nothing else is a source. No repo, page, email, or agent keeps its own divergent copy of the values. When a surface and the design sample of record (the approved v5 email) disagree, the email's treatment governs until James rules otherwise.

2.2 A per-repo anchor

Each repository carries the anchor — four artifacts, defined in the rollout plan:

  1. DESIGN.md at the repo root: one read that gives any human or agent opening the repo the non-negotiables and the pointer to the canonical tokens.
  2. An agent-instructions block in the repo's agent-instructions file (AGENTS.md / .github/muse-instructions.md), so the encounter with the system is unavoidable before branded work starts.
  3. The car-wash workflow and a design-wash.json declaring the repo's wash targets, wired so the repo's deploy path depends on the wash (Section 2.3).
  4. A token link, not a token copy. The anchor points at the canonical tokens.json / tokens.css; surfaces resolve values from there (or from a build step that pulls them), so a versioned amendment propagates instead of stranding dozens of divergent copies.

New repos are born anchored: the template set is part of repo creation, so the estate stops growing unanchored repos.

2.3 The car wash in the deploy path

The design gate (~/workspace/tools/design-gate/, currently v0.2) is the wash: one command —

node gate.mjs <page-file-or-local-url> [--out <dir>] [--wordmark <css-selector>]

— that runs four checks and exits non-zero on any failure (exit 0 pass · 1 fail, with the failures named · 2 gate could not run):

  1. Palette lint. Every hex color in the page must be one of the eight house tokens, with occurrence counts named for any offender. For URL targets, the page's same-origin stylesheets are fetched and linted with the HTML — a served app's palette lives in its CSS. Inline script contents are excluded from the corpus (framework payloads are not authored design); authored colors render through stylesheets, style elements, and style attributes, all of which stay in the corpus. A fully transparent hex (alpha 00) renders as no color and is counted, never a violation; a semi-transparent color lints on its RGB, so a black scrim must be an ink scrim.
  2. Renders. Full-page screenshots at 420px (phone) and 1280px (desktop), saved beside the report as evidence.
  3. Wordmark one-line check at 420px, measured on the live render, in two parts: the wordmark element must carry white-space: nowrap (the guarantee — rendered fit in one engine is font-metric luck, and the 2026-11-18 wrap reached a phone whose render differed from desktop Chromium), and it must occupy exactly one line (rendered height ÷ computed line-height ≤ 1.25) with no horizontal overflow. The rendered-lines measure is live independently: a forced break fails even with nowrap present. On component-built sites the wordmark is not the header h1; --wordmark <css-selector> names the element that carries it (uze-web: --wordmark ".wordmark"). The rule checked is identical.
  4. Axe accessibility floor. axe-core runs on the 420px render; violations are printed by rule id with impact and node count, and recorded in the report. Findings are currently report-only — a deliberate posture, so pre-existing findings do not train everyone to ignore the gate. Promoting violations of impact critical/serious to hard failures is the documented next step for the gate.

In CI, the wash is a required job on the repo's deploy path: the deploy job needs: the wash, so a failed wash fails the deploy — no wash, no deploy. The wash's evidence (report plus both screenshots) is uploaded as a run artifact on every run.

The gate was proven before it was wired anywhere, under the rule that every check must be able to fail: the current Dev Library page passes (exit 0); a mutant with the exact red that shipped on 2026-11-18 reintroduced fails, naming the palette violation; a mutant with the wordmark's nowrap removed fails, naming the one-line violation — even though that mutant still happens to render on one line in headless Chromium, which is precisely why the check enforces the rule and not just the render. The full record is in the gate's PROOF-2026-11-19.md.

The wash is mechanical and visual. The gate's screenshots are looked at by the builder before ship — because the three-second test (Section 3.5) is judgment, and judgment is in the checklist, not the linter.

2.4 White-label: token value overrides only

A tenant engagement supplies one override file (tenant.tokens.json, kept with the tenant's deployment configuration) containing only the keys they override, in the same schema as the canonical tokens. At build/deploy time the deployment's effective tokens are computed — canonical tokens with the override values merged over them, key by key — the surface is built from the effective tokens, and the gate runs against the effective tokens, plus every structural check unchanged.

A tenant may override values only:

  • Palette values — a full re-palette is allowed; it is still exactly eight tokens, one accent, and no hue outside the tenant's own declared set. The no-conventional-status-hues rule binds tenants too.
  • Wordmark text and logo — the companion word or product name beside the mark, and a tenant logo asset — subject to the structural wordmark rules, including one line at every width.
  • Type families — family substitution only; the scale relationships do not move. Licensed fonts are the tenant's responsibility.
  • Imagery — real hosted assets; never emoji as icons, never placeholder boxes in a shipped page.

A tenant may never override:

  • The one-line wordmark rule (a tenant name that doesn't fit gets smaller, never wrapped).
  • Type-scale relationships (headline > card title > section head > body > secondary > meta, at the canonical ratios).
  • Component geometry (pill buttons at radius 999px, card radius and hairline borders, band treatments, hairline-only dividers, outline-only tags).
  • The feedback rule (status renders in the text token with the accent marker; no tenant gets red/green status colors — the rule is structural, not a UZE palette preference).
  • The accessibility floor (a tenant palette whose accent fails contrast on its ground fails the wash; the fix is a tenant value change, never a waived check).
  • The car wash itself (no tenant deployment path may skip, weaken, or self-certify the gate; same gate, same exit codes, same evidence per deploy).
  • The three-second test (no version numbers, runtimes, or production notes on any public tenant surface either).

A tenant value change is an edit to their override file plus a passed wash — no approval from James needed for tenant-internal values. A request that needs a structural change is not a tenant override at all: it is a design-system amendment (Section 2.5), ratified by James, and then available to every deployment. Tenants are never forked onto private structures. Full spec: ~/workspace/design-anchor/tenant-override.spec.md.

2.5 Advisory input as amendments, never as edits

When James, Jonathan Schmidt, or his Fort Lauderdale motion-graphics collaborator steers the design, the input lands as a versioned amendment to tokens.json — version bump plus a dated note in the house skill — ratified by James. It then propagates to every anchored repo at once, because they all resolve from the one source.

The change rule is stated in the canonical file itself: changes are proposed by SoSem or by the design advisory channel (Jonathan Schmidt and his Fort Lauderdale motion-graphics collaborator) and ratified by James. A page-level edit is never a design-system change. No one-off page edits, no drift between surfaces, and every change carries a version and a date.

3. The non-negotiables

These are the rules the anchor states, the gate enforces where enforcement is mechanical, and the pre-ship checklist carries where it is judgment. They are transcribed from the system James approved — the v5 email — and ratified with the house skill on 2026-11-19. Nothing in this section is a proposal.

3.1 Palette only — eight tokens, no other hues

"Creamsicle" is James's term for the lighter tint of the brand tangerine — the pale peach accent of the system.

No other hues. Ever. Status feedback included. Never red, green, blue, amber, or any "conventional" status color, on any surface — pages, emails, documents, generated surfaces. Convention is not a source; this palette is. Opacity/tint derivatives of the eight tokens are the only permitted variation, and a new tint is a system change: it is recorded as an amendment ratified by James, never introduced inside a page. (This is the exact question currently open on uze-web — see Section 4.2.)

3.2 The wordmark never wraps

  • "UZE" is always tangerine #ff6b00. The word that follows is white reversed out of ink (on a band) or ink (on a light ground). Never tangerine-on-tangerine, never muted.
  • Forms of record: UZEmarkets · UZE Dev Library · UZE + a letter-spaced eyebrow in band-muted.
  • One line at every width, phone included. white-space: nowrap on the wordmark element; at ≤620px the size steps down (of record: 29px → 23px) — reduce the size, never accept the wrap. A wrapped wordmark is a build failure, on the same level as a failed test.
  • Footer form: © 2026 UZEmarkets centered in an ink band — "UZE" tangerine, linking to https://uzemarkets.com, plain wordmark look, no underline; "markets" white.

3.3 Components and layout

  • Buttons are black pills: ink background, white text, border-radius: 999px, sans 700. Primary padding 14px 34px (email) / 11px 22px (page). Secondary: white pill, ink text, ink border. No square buttons, no colored buttons.
  • Cards: white surface, 1px hairline border, radius 14px, padding 28px 34px (24px 20px at ≤620px).
  • Dividers are hairlines: 1px #ddd5c9, full width — never heavy rules, never colored rules.
  • Ink bands carry reversed-out content: white display text, tangerine wordmark accent, band-muted eyebrows; radius 14px, padding 20px 34px.
  • Creamsicle soft bands carry centered ink content: #FDEEE2 fill, radius 12px, padding 26px 24px, serif headline 21px.
  • Tags are tangerine outline pills — 1px tangerine border, tangerine text, radius 999px, 12px/700 — outline, never filled.
  • Links are tangerine, weight 700; underlined in body copy, no underline in the wordmark/footer treatment.
  • Facts lists use the tangerine "—" marker at weight 800.
  • Page frame: max-width 880px centered, cream ground. Generous whitespace is part of the system (the Maple-modeled language James approved) — spacing is not compressed to fit more in.
  • Imagery: real hosted assets; never emoji as icons or decoration; never placeholder boxes in a shipped page.

3.4 Type

  • Display: Georgia serif (Georgia, 'Times New Roman', serif) — headlines, card titles, FAQ summaries, banner headlines. Serif is for display only; body copy set in serif throughout is an out-of-system error.
  • Body: system sans (-apple-system, 'Segoe UI', Roboto, Helvetica, Arial, sans-serif).
  • Scale of record:

3.5 Feedback and states

  • Error, success, and notice text renders in ink. An error additionally takes the tangerine "—" marker (the email's facts marker) at weight 700. Success is plain ink.
  • Feedback sits directly under the control it concerns, and says what happened and what to do next, in plain words.
  • Disabled and loading states use muted text and reduced emphasis within the palette — no new colors.
  • Anti-enumeration silence, where a flow requires it (for example sign-in codes), is a behavior rule of that flow, not a styling exception; the visible message still follows this section.

3.6 The pre-ship check and the three-second test

No page ships without the house skill's §6 check, run in order — a failure at any step stops the ship:

  1. Render the final page in headless Chromium at 420px and 1280px; screenshot both, full page.
  2. Look at both screenshots — the builder's own eyes on the actual render, not the code. Completion is an observable result in the running system.
  3. Wordmark check: one line at 420px, tangerine UZE, correct companion color.
  4. Palette check: every color value in the shipped markup/styles against the tokens — status colors included.
  5. Three-second test (James's): the first phone screen carries title, subject, hook — and nothing else competes with them. No version numbers, word counts, runtimes, or production notes anywhere public.
  6. Component pass: pills are pills, dividers are hairlines, bands reverse out correctly, creamsicle bands carry ink text, cards match §3.3.
  7. Accessibility floor: axe-core (or Lighthouse) — no contrast or label violations ship. Automation catches roughly half of WCAG issues; it is a floor, not a certificate. The standing references behind the system are the Nielsen Norman Group usability heuristics and WCAG 2.2 AA.
  8. Regression guard: where the app has a test suite, add the assertions that would have caught the failures of record (palette-token presence plus off-palette absence; wordmark nowrap), so the next change cannot silently reintroduce them.

The delivery report states the check's result — screenshots, palette result, test tally. A delivery report that makes James ask "have we tested?" is a failed report.

Steps 1, 3, 4, and 7 are mechanized by the car wash (Section 2.3). Steps 2, 5, 6, and 8 are the builder's — judgment, deliberately kept human (Addendum, Pillar 7).

ADDENDUM — Pillars of the Human Design Surface

The mechanism in Section 2 rests on seven pillars. Each is stated as a principle, then grounded in what the system actually does today. A pillar is load-bearing in the plain sense: remove it, and a named failure from the record returns.

Pillar 1 — One canonical source of values

Principle. Every design value in the ecosystem exists in exactly one place, and every surface resolves its values from that place.

In the system. ~/workspace/design-anchor/tokens.json (v1.0.0, RATIFIED) holds the palette, type scale, component geometry, wordmark rules, and the no-other-hues rule. tokens.css is generated from it and was verified mechanically identical in value sets. The house skill carries the same system as rules in words. Repos hold links, never copies (Pillar 5's overrides and Section 2.2's anchors both resolve back to this file). The file's own meta states the rule: every repo anchor, the design gate, and every tenant deployment resolve their values from this file or from a versioned amendment to it — no repo keeps its own divergent copy.

What it prevents. Drift by accumulation: forty repos each remembering the palette slightly differently, until "the brand" is forty approximations. With one source, an amendment is one edit with a version and a date, and it propagates everywhere at once.

Pillar 2 — Palette only: no hue exists outside the tokens

Principle. The eight tokens are not the preferred colors. They are the only colors. A hue that is not in tokens.json does not exist on any UZE surface — in layout, in components, in charts, and in status feedback above all.

In the system. Ink #1a1a1a, cream #f5f2ee, tangerine #ff6b00, creamsicle #FDEEE2, hairline #ddd5c9, muted #6b655e, band-muted #b8b0a4, white #ffffff. Errors, successes, and notices render in ink; an error adds the tangerine "—" marker. Red, green, blue, and amber are forbidden by name in the canonical file's rule and in the house skill. The palette lint enforces the pillar mechanically on every wash: any other hex is a named failure with its occurrence count. Opacity/tint derivatives of the tokens are the only permitted variation, and a genuinely new tint is an amendment (Pillar 6), never a page-level decision.

What it prevents. The 2026-11-18 failure exactly: red #1a1a1a and green #1a1a1a status colors in a page whose approved system contains neither — introduced because convention ("errors are red") silently outranked the system. Under this pillar, convention is not a source. The pillar is also why the four uze-web tint/shade hexes in Section 4.2 are an open ruling rather than a quiet exception: the system does not do quiet exceptions.

Pillar 3 — The wordmark never wraps

Principle. The wordmark is one line at every width, on every surface, without exception. If it does not fit, it gets smaller. It never breaks.

In the system. "UZE" is always tangerine; the companion word is white reversed out of ink or ink on a light ground — never tangerine-on-tangerine, never muted. The element carries white-space: nowrap; at ≤620px the size steps down (of record, 29px → 23px). A wrapped wordmark is classified as a build failure, on the same level as a failed test. The gate checks the pillar two ways at 420px: the computed nowrap must be present (the guarantee), and the rendered result must be exactly one line with no horizontal overflow (the confirmation) — each measure able to fail on its own, as the gate's mutant proofs show. On component-built sites, --wordmark names the element that carries the mark; the rule checked is identical. The footer form is fixed: © 2026 UZEmarkets, "UZE" tangerine linking to https://uzemarkets.com, no underline.

What it prevents. The other 2026-11-18 failure: "UZE Dev Library" reaching the founder's phone with "Library" alone on line two — although it plainly fits on one line. The pillar's sharp edge is the nowrap requirement: a wordmark that merely happens to fit in one rendering engine is luck, and the system does not ship luck.

Pillar 4 — The car wash: no page deploys unwashed

Principle. Verification is not a step a builder remembers to do. It is a gate in the deploy path that a page cannot pass without satisfying — palette lint, renders at phone and desktop widths, the wordmark check, and the accessibility floor, with the evidence kept.

In the system. The design gate (~/workspace/tools/design-gate/, v0.2) runs as a required CI job; the deploy job needs: it, so a failed wash fails the deploy. Exit codes are part of the contract: 0 pass, 1 fail with named failures, 2 gate could not run — and "could not run" is not a pass. Every run retains its evidence (report plus 420px and 1280px screenshots) as a deploy artifact. The gate was proven able to fail before it was trusted to pass anything: injected off-palette color, removed nowrap, and a forced break each fail with the violation named. The first fully-anchored deploy (Section 4.1) is this pillar operating end to end — wash SUCCESS, then deploy SUCCESS, in that order, in CI, on the record. Axe findings are report-only today by deliberate posture; promoting critical/serious findings to hard failures is the documented next step, and when it lands it lands as a versioned gate change, not a quiet tightening.

What it prevents. The whole class of failure the founder named on 2026-11-18: simplistic errors he had to catch manually, by eye, on his phone, across repeated iterations — because nothing mechanical stood between a page and production. The pillar moves the catching to the deploy path, where it happens every time, the same way, whether or not anyone is watching.

Pillar 5 — White-label by token override only: the sensitivity stays resident

Principle. A tenant changes values. A tenant never changes structure, and never touches the wash. The design sensitivity therefore survives white-labeling intact — it is resident in the deployment, not loaned to it.

In the system. The tenant supplies one file, tenant.tokens.json, holding only the keys they override. Effective tokens are computed by merging those values over the canonical set; the surface builds from the effective tokens; the gate runs against the effective tokens with every structural check unchanged. Overridable: palette values (still exactly eight tokens, one accent, no hue outside the tenant's declared set, no conventional status hues), wordmark text and logo, type families, imagery. Never overridable: the one-line wordmark rule, type-scale relationships, component geometry, the feedback rule, the accessibility floor, the three-second test — and the car wash itself, which no tenant path may skip, weaken, or self-certify. A tenant palette that fails contrast fails the tenant's deploy; the fix is a value change, never a waived check. A request for structural change leaves the tenant channel entirely and becomes a system amendment under Pillar 6.

What it prevents. The usual white-label dilution: the tenant's team edits pages directly, the standard degrades into a PDF nobody opens, and the enterprise client's product quietly becomes sloppy in ways the client can feel but not name. Here the only tenant-writable surface is a value file the gate reads. The tenant can make the product unmistakably theirs; they cannot make it off-system or unwashed — and neither can we, on their behalf or ours.

Pillar 6 — Advisory input as ratified amendments, never page edits

Principle. Design steering — from James, from Jonathan Schmidt, from his Fort Lauderdale motion-graphics collaborator — enters the system as versioned, ratified amendments to the canonical source. It never enters as an edit to a page.

In the system. The canonical file's change rule names the channel: amendments are proposed by SoSem or by the design advisory channel and ratified by James, landing as a version bump to tokens.json plus a dated note in the house skill. Because every anchor resolves from the one source (Pillar 1), a ratified amendment propagates to the whole estate at once — no surface is left carrying the old value, and no surface carries a private improvement the rest of the ecosystem never received. Tenant structural requests route into this same channel (Pillar 5). The house skill's own history is the pattern: drafted 2026-11-19, ratified by James's tap at 11:15 ET the same day, standing practice from that tap — a version, a date, a named ratifier.

What it prevents. Two opposite failures: drift (good input applied to one page and lost to the rest) and capture (a change entering the system without the founder's ratification because it arrived as a small edit somewhere). Under this pillar every design decision has exactly one door, and the door has a name and a date on it.

Pillar 7 — Judgment stays human: the three-second test and the looked-at render

Principle. Automation is the floor; the look is the standard. The checks that are judgment — hierarchy, emphasis, whether the first screen earns its three seconds — are assigned to human eyes by rule, and are never delegated to the linter or averaged into a score.

In the system. The house skill's pre-ship check requires the builder to look at both screenshots — the actual render, not the code — and applies James's three-second test: the first phone screen carries title, subject, hook, and nothing else competes with them; no version numbers, word counts, runtimes, or production notes anywhere public. The car wash produces the renders on every run precisely so the look has something to land on; the gate report records the mechanical results, and the delivery report carries the wash result — screenshots, palette result, test tally — so the judgment is exercised on evidence, not on recollection. The supporting practice is named in the skill: the Nielsen Norman Group heuristics for flows, WCAG 2.2 AA as the accessibility floor, and the rule that completion is an observable result in the running system, not a claim about the code.

What it prevents. The false comfort of a green checklist on a page no one actually looked at — the failure mode in which every automated check passes and the page is still wrong in the way only a person glancing at a phone would notice in three seconds. The founder's eye caught the 2026-11-18 errors because his eye was the only check standing. This pillar keeps the eye — his, the builder's, the advisors' — and removes its loneliness: it is now the last check in a line, not the only one.
